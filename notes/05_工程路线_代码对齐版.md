# 2. 项目背景

NebulaRPC 是一次工程重构项目：

- 从 MyMuduo 迁移成熟网络层能力（Reactor / TCP / Buffer / 多线程）
- 从 game_rpc_project 迁移 Protobuf RPC 能力（Generic Service / request_id / framing）
- 在新的工程结构中继续演进为完整 RPC Framework

最终形态：

```
Linux Reactor Runtime
        +
TCP Transport
        +
RPC Protocol
        +
Async Runtime
        +
Client Runtime
        +
Observability
        +
Performance Engineering
```

参考方向：gRPC / bRPC 类工业 RPC 框架。

构建基线：

- 仅支持 Linux（CMake 中 `FATAL_ERROR` 拦截非 Linux 平台）
- C++20（`CMAKE_CXX_STANDARD 20`，无扩展）
- 警告：`-Wall -Wextra -Wpedantic -Wconversion -Wshadow`
- Presets：`linux-debug` / `linux-release` / `linux-asan` / `linux-ubsan`
- 依赖：protobuf、spdlog、ninja、g++（Ubuntu 22.04 系统包，不 vendor 源码）

# 5. 已完成 Phase 细节

## 5.1 Phase 1 网络核心层

### EventLoop

职责：IO 事件循环 + 跨线程任务 + 定时器统一入口。

核心循环：

```
epoll_wait (Poller::Poll, 10s 超时)
     |
     v
active_channels -> Channel::HandleEvent
     |
     v
DoPendingFunctors（跨线程任务）
```

关键机制：

- `eventfd` 唤醒：`QueueInLoop` 后非 owner 线程或正在执行 functor 时 `WakeUp()`，
  保证 `epoll_wait` 不会睡过新任务。
- `thread_local` 保证一个线程只有一个 EventLoop。
- `RunInLoop`：owner 线程直接执行，否则转 `QueueInLoop`。
- `RunAt / RunAfter / CancelTimer` 全部委托 `TimerQueue`。

### Channel / EPollPoller

- Channel 封装 fd 与 events/revents，`Tie(shared_ptr)` 用 weak_ptr 保证
  `HandleEvent` 期间属主对象不被析构。
- EPollPoller 使用 **LT 模式**，`index_` 三态（kNew/kAdded/kDeleted）
  决定 `EPOLL_CTL_ADD/MOD/DEL`。

### Buffer

解决 TCP 字节流无消息边界：

- `ReadFd` 用 `readv` + 64KB 栈上扩展缓冲，一次系统调用读尽，
  避免先猜大小再二次读取。
- `PeekUInt32 / Retrieve` 支撑上层增量解码。
- `kCheapPrepend = 8` 预留前置空间。

### TcpConnection

- 四态状态机：`kConnecting -> kConnected -> kDisconnecting -> kDisconnected`。
- `Send`：owner 线程直接 `SendInLoop`；跨线程则 `shared_from_this` 投递，
  绝不捕获裸 `this`。
- `SendInLoop`：先尝试直接 `write`，写不完进 `output_buffer_` 并 `EnableWriting`，
  `HandleWrite` 可写时续写，写完后触发 `WriteCompleteCallback`。
- 构造即 `SetTcpNoDelay(true)`。

### TcpServer / Acceptor / EventLoopThreadPool

- Acceptor 监听 fd，新连接交给 TcpServer。
- TcpServer 通过 `EventLoopThreadPool::GetNextLoop()` round-robin 分配 IO 线程，
  `ConnectEstablished` 投递到连接所属 loop 执行。
- 连接表 `connections_` 由主 loop 维护，`RemoveConnection` 先回主 loop 摘除
  再投递到 IO loop 销毁。

### Connector / TcpClient

- 非阻塞 `connect`：`EINPROGRESS` -> 注册 `EPOLLOUT` -> 可写后
  `getsockopt(SO_ERROR)` 判定真正结果。
- `RemoveAndResetChannel` 延迟释放 Channel（可能仍在 `HandleEvent` 调用栈中）。
- Channel 回调用 `weak_ptr<Connector>` 打断引用环。
- 注意：**当前 Connector 连接失败后不会自动重连**（`connect_ = false` 即停止），
  重连属于 Phase 9 内容。

## 5.2 TimerQueue（Phase 1.5）

- `timerfd_create(CLOCK_MONOTONIC)` 把时间事件变成 fd 事件，
  与 socket fd / eventfd 一起进 `epoll_wait`，Reactor 不需要轮询时间。
- 数据结构：`multimap<TimePoint, timer_id>`（按到期时间排序）
  + `unordered_map<timer_id, Timer>`（O(1) 找回调）。
- 新增/取消定时器只在"影响最早到期时间"时才 `timerfd_settime` 重置。
- 时钟用 `steady_clock`：单调，不受系统改时间影响。

## 5.3 Phase 2 RPC 基础层

### 帧格式（rpc_codec.cpp 实际实现）

```
+------------------+ 4B frame_size（网络序）= meta_size 字段 + meta + payload 的总长
| frame_size       |
+------------------+ 4B meta_size（网络序）
| meta_size        |
+------------------+
| RpcMeta protobuf |
+------------------+
| payload protobuf |
+------------------+
```

约束与防御：

- `kMaxFrameSize = 16MB`：超限直接 `kError`，防止恶意/错误长度打爆内存。
- `Decode` 三态：`kNeedMore`（半包，保留 Buffer 数据）/ `kOk` / `kError`。
- `DecodeBody` 校验：meta 长度不越界、meta 可解析、`payload_size` 与实际一致。
- 服务端/客户端都在 `OnMessage` 里 `while(true)` 循环解码，一次 read 多帧全部取出（粘包）。

### RpcMeta（rpc_meta.proto）

```
type: REQUEST / RESPONSE / ERROR
request_id: uint64
service_name / method_name（仅 REQUEST）
payload_size: uint32
error_code / error_text（ERROR）
```

### RpcServer

- `RegisterService`：按 `service->GetDescriptor()->full_name()` 注册。
- 分发链：`FindMethodByName` -> `GetRequestPrototype/GetResponsePrototype` 动态建消息
  -> `ParseFromString` -> `service->CallMethod`。
- 异步 Service 生命周期：`ServerCall`（request/response 的 unique_ptr）
  被 `RpcClosure` lambda 捕获 `shared_ptr`，活到 `done->Run()` 发完响应为止。
- 错误回包：404（service/method not found）、400（非 REQUEST 帧 / parse 失败）、
  500（序列化失败），走 `RpcMeta::ERROR` 帧。
- 已知限制：`CallMethod` 传入的 controller 是 `nullptr`，
  服务端目前没有 per-call controller（Phase 6 服务端取消、Phase 5 服务端 deadline
  检查都要从这里补）。

### request_id

- `RpcChannel::next_request_id_` 是 inline static atomic，全进程单调递增。
- 一个 TCP 连接上多请求并发飞行，响应乱序到达时按 `request_id` 关联
  `PendingCall`，不依赖顺序假设。

## 5.4 Phase 3 Async RPC（已完成）

`RpcChannel` 当前模型（与旧文档"建议"相比，已经全部落地）：

```
业务线程: stub.Echo(controller, req, resp, done)
    |
    v
CallMethod（可在任意线程）
    - done == nullptr 直接拒绝（纯异步，不提供同步路径）
    - SerializeToString -> 分配 request_id -> RpcCodec::Encode
    - RunInLoop(RegisterAndSend)
    - 立即返回
    |
    v  （以下全部在 RpcChannel 属主 EventLoop 线程）
RegisterAndSend
    - 已断连 -> 立即失败完成
    - deadline 已过 -> 立即 "RPC timeout" 完成
    - pending_calls_[request_id] = PendingCall
    - 有 deadline -> loop_->RunAt(deadline, OnTimeout)
    - 已连接 -> connection_->Send
    - 未连接 -> pending_writes_ 排队，等 OnConnection 冲刷
    |
    v  （网络事件稍后到达）
OnMessage -> Decode -> HandleFrame -> CompleteCallWithFrame
    - TakePendingCall(request_id) 摘除
    - 反序列化 response / 设置 error
    - done->Run()（在属主 loop 线程）
```

关键设计点：

1. **连接前写排队**：`pending_writes_` 允许连接建立前发起 RPC；
   连接成功后冲刷时会跳过已被 timeout/断连完成的 request_id。
2. **断连失败全部 pending**：`OnConnection(disconnect)` / `OnConnectError` /
   协议错误 / 析构，四条路径都会 `FailAllPending`，保证 done 一定执行、
   pending 不泄漏。
3. **回调线程语义**：`done->Run()` 固定在属主 EventLoop 线程。
   业务回调里不能阻塞，否则整个 Reactor 停摆。

> 技术决策说明：为什么 `pending_calls_` 不加 mutex
>
> 为什么是这个方案：
>   所有读写都通过 `RunInLoop/QueueInLoop` 收敛到属主 EventLoop 线程，
>   用线程归属消灭共享并发，比加锁更简单、无竞争、状态机更容易推理。
>
> 底层是什么：
>   不是"map 天然安全"，而是 Reactor owner-thread 模型——
>   跨线程操作先经 `eventfd` 唤醒再在目标线程串行执行。
>
> 如果是你你会怎么学：
>   对照 muduo 的 "one loop per thread" 章节；
>   注意这个前提在 Phase 6（跨线程 Cancel）引入后会被部分打破，见第 6.2 节。

## 5.5 Phase 5 Timeout / Deadline（已完成）

实际链路：

```
RpcController::SetTimeout(100ms) / SetDeadline(tp)
    |
    v
ResolveDeadline(controller)
    deadline 优先；否则 now + timeout；都没有 -> 无定时器
    |
    v
RegisterAndSend: loop_->RunAt(deadline, OnTimeout(request_id))
    |
    v
到期: TimerQueue -> OnTimeout -> CompleteCallWithFailure("RPC timeout")
    |
    v
TakePendingCall 摘除 -> CancelTimer 已不需要（自身就是定时器触发）
    -> controller->SetFailed -> done->Run()
```

Exactly-Once 当前实现（旧文档三个 Case 的覆盖方式）：

- Case 1（Response 先到）：`TakePendingCall` 摘除时 `CancelTimer`，
  定时器不会触发；即使触发也找不到 request_id。
- Case 2（Timeout 先到）：`OnTimeout` 摘除 pending；迟到的 response
  在 `CompleteCallWithFrame` 里找不到 request_id，直接丢弃。
- Case 3（并发竞争）：**当前由单线程串行天然化解**——response 事件和
  timer 事件都在同一个 EventLoop 线程排队执行，不存在真正并发。
  这正是旧文档没有预见到的简化：因为 timeout 走的是同一个 loop 的
  `TimerQueue`，竞争被线程模型消灭了。

> 技术决策说明：当前 Exactly-Once 为什么用"摘除 map"而不是 CAS 状态机
>
> 为什么是这个方案：
>   单线程模型下，`TakePendingCall` 一次摘除 = 一次完成，
>   不需要原子操作，代码直白；`RpcCall::TryComplete`（CAS）目前无用武之地。
>
> 底层是什么：
>   "谁先拿走 pending 谁负责完成"是所有权转移；
>   CAS 状态机是"谁先改状态谁负责完成"，两者等价，但适用线程模型不同。
>
> 如果是你你会怎么学：
>   等到 Phase 6 跨线程 Cancel 引入后，单线程假设被打破，
>   届时再对比 `rpc_call.h` 的 `compare_exchange_strong` 方案，
>   理解为什么多完成源跨线程时必须用 CAS。

## 6.1 Phase 4 RpcCall 状态机（已完成）

接线前现状（历史留档）：

- `rpc_call.h/.cpp`：`RpcCallState { Pending, Completed, Cancelled, Timeout, Failed }`
  + `TryComplete(state)` 用 `compare_exchange_strong(Pending -> state)`
  保证只能成功一次；但当时 git 未跟踪、未进 CMake、`RpcCall` 零引用。
- `rpc_call_context.h`：原打算用 `RpcCallContext` 整体替换 `PendingCall`，
  后判定为**死文件**（全仓零引用），最终方案改为 `PendingCall` 内嵌
  `RpcCall`，**不替换结构**。

接线方案与实际结果：

```
第一步：PendingCall 内嵌 RpcCall（不采用整体替换 RpcCallContext）   [完成]
第二步：所有完成路径先过状态门：
    Response  -> call.TryComplete(Completed)
    Timeout   -> call.TryComplete(Timeout)
    Disconnect-> call.TryComplete(Failed)
    Cancel    -> call.TryComplete(Cancelled)
    TryComplete 返回 true 才允许 TakePendingCall + 执行回调          [完成]
第三步：rpc_call.cpp 加入 CMake                                   [完成]
第四步：状态机单测（单线程 + 多线程竞争）tests/rpc_call_test.cpp      [完成]
```

接线后 `TryComplete` 在当前单线程模型下仍然"总是第一个成功"，
看起来像多余的一层——它的价值在 Phase 6 跨线程 Cancel 才兑现。
先接线是为了让 Cancel 到来时不需要再动 `RpcChannel` 的骨架。

## 6.2 Phase 6 Cancel（已完成）

接线前缺口（历史留档）：

```
1. RegisterAndSend 注册 pending 后没有向 controller 注册 cancel 回调，
   StartCancel 调了也没人响应。
2. 没有 Cancelled 完成路径，RpcCallState::Cancelled 无人使用。
3. RpcController 没有反注册接口：RPC 正常完成后，channel 注册的
   cancel 回调仍留在 cancel_callbacks_ 里，业务复用或析构 controller
   时有悬挂风险。
```

实际落地：

```
RegisterAndSend 内：
    RegisterOnCancel(RpcClosure: RunInLoop -> TryComplete(Cancelled)
                                 -> 成功则 TakePendingCall + done)   [完成]

TakePendingCall 内（四条完成路径唯一收口）：
    RemoveOnCancel(token)                                          [完成]
```

`NotifyOnCancel`（protobuf 虚函数签名）保持不动，新增带 token 的
`RegisterOnCancel / RemoveOnCancel` 一对：token 用来在完成后精确摘除，
返回 -1 表示 controller 已取消、回调已内联执行（所有权已转移）。

关键难点（为什么 Cancel 比 Timeout 难）：

- `StartCancel` 是**第一个来自任意业务线程的完成源**。
  Timeout 和 Response 都在属主 loop 内串行，Cancel 不是。
- 因此 Cancel 路径是 `RpcCall::TryComplete`（CAS）真正派上用场的地方：
  业务线程 `StartCancel` 与 loop 线程 response 到达同时发生时，
  靠 `compare_exchange_strong` 保证只有一方完成。

> 技术决策说明：为什么 Cancel 必须走 CAS 而不是继续靠单线程串行
>
> 为什么是这个方案：
>   `StartCancel` 的语义就是"任意线程随时取消"（protobuf 接口如此约定），
>   把它强制投递到 loop 线程再判断会引入额外时延和复杂度；
>   直接在两个线程上对同一个原子状态做 CAS，谁赢谁完成，最简洁。
>
> 底层是什么：
>   `compare_exchange_strong(expected=Pending, desired=Cancelled)`
>   对应 CPU 的 CMPXCHG 原子指令，失败说明别人已完成，直接放弃。
>
> 如果是你你会怎么学：
>   写一个测试：一个线程循环 `StartCancel`，loop 线程立刻回 response，
>   用 ASan + 计数断言 done 恰好执行一次。这个测试就是 Phase 4 接线
>   是否正确的最终裁判。→ 已实现在 `tests/rpc_cancel_test.cpp`。

接线过程中额外发现并修掉四个生命周期缺陷（终态语义 / 析构释放 /
定时器裸 this / 守卫位置 + AliveGuard atomic），见 `06` 的 5.5。

后续增强（不在本轮）：

- 服务端取消通知（需要 `RpcMeta` 增加 CANCEL 类型 + 服务端持有 in-flight 表）。
- 取消后的资源释放统计。

# 7. 未开始 Phase：设计与代码接入点

## 7.1 Phase 7 C++20 Coroutine RPC

目标：

```
现在:  stub.Echo(controller, &req, &resp, done);   // callback
将来:  auto resp = co_await client.Echo(req);      // coroutine
```

接入点（都在现有代码上改，不需要新网络层）：

- 完成路径 `CompleteCallWithFrame / CompleteCallWithFailure`
  目前最后执行 `done->Run()`——协程版把它换成
  `coroutine_handle.resume()`（或投递到指定 executor 再 resume）。
- `PendingCall` 增加一个 `std::coroutine_handle<>` 字段
  （或 Awaiter 对象指针），`await_suspend` 时写入。

需要实现的组件：

```
RpcAwaiter
    await_ready   -> false
    await_suspend -> 把 handle 挂到 PendingCall，发起 CallMethod
    await_resume  -> 返回 response 或抛出/返回 controller 错误
promise_type      -> 管理协程帧生命周期与异常传递
```

必须想清楚的问题：

- **resume 在哪个线程**：当前完成都在属主 loop 线程，
  协程会在网络线程上继续执行业务代码。语义上可接受（与 done 回调一致），
  但要在文档中写死；若业务要求回原线程，需要引入 executor 投递。
- **协程帧生命周期**：`await_resume` 之前 response/controller 必须活着，
  现有 `shared_ptr<CallContext>` 用法（见 `rpc_echo_client.cpp`）可直接沿用。
- 构建：g++ 11 + `-std=c++20` 即可，CMake 无需改标准。

## 7.2 Phase 8 Backpressure

三个无上限资源，对应三个限制点：

| 资源 | 现状 | 限制方案 |
|---|---|---|
| `TcpConnection::output_buffer_` | 无上限，慢客户端会撑爆内存 | 高水位回调（HighWatermark）：超过阈值通知上层停发/断连 |
| `RpcChannel::pending_calls_` | 无上限 | `max_pending_calls`：超限直接 `SetFailed("too many pending rpcs")` 拒绝 |
| `RpcChannel::pending_writes_` | 无上限 | 与连接状态绑定，连接建立后冲刷；超限拒绝新 RPC |

策略三选一（按场景）：

```
reject   直接拒绝，快速失败（默认）
queue    有界排队，满了转 reject
degrade  返回降级结果（业务层实现，框架只提供钩子）
```

服务端对称问题：单连接输入 Buffer 无总量上限（只有单帧 16MB 限制），
需要在 `TcpConnection` 增加输入水位检查，超限 `Shutdown`。

## 7.3 Phase 9 Client Runtime

现状：`RpcChannel` = 1 个 `TcpClient` = 1 条连接 = 1 个 loop。

目标架构：

```
Application
    |
RpcClient（新对象）
    |
    +-- ConnectionPool：N 条 RpcChannel/连接
    |       - 空闲复用 / 健康检查 / 上限管理
    |
    +-- LoadBalancer
    |       - 第一版 Round Robin
    |       - 后续 Least Connection -> Consistent Hash
    |
    +-- Retry / Reconnect 策略
```

接入点：

- 连接复用：`EventLoopThreadPool` 服务端已有，客户端可复用同一套
  做多 loop 分布。
- 重连：当前 `Connector` 失败即停（`HandleConnectError` 置 `connect_ = false`）。
  需要增加带退避的重连定时器（`RunAfter` 已具备），
  重连成功后 `RpcChannel` 的 `pending_writes_` 冲刷机制可以直接复用。
- Retry 前提：只重试幂等接口；次数 + 指数退避；
  注意与 Phase 5 deadline 的关系——重试不能突破总 deadline。

## 7.4 Phase 10 Observability

现状：`logger.h` 提供了 `NLOG_*` 宏，spdlog 已链接进 `nebula_rpc`，
但 RPC 层**没有一处日志调用**。

三步走：

1. **结构化日志**：在 `CallMethod` 发起与完成路径记录
   `request_id / service / method / latency / error`；
   协议错误、断连、超时各一条。
2. **Metrics**：每 method 统计 QPS、latency 直方图（P50/P95/P99）、
   timeout/error 计数；先用进程内原子计数 + 周期打印，
   不急着接 Prometheus。
3. **Graceful Shutdown**：`TcpServer` 目前没有 `Stop`。
   流程：停止 accept -> 等待 in-flight RPC 完成（有上限时间）
   -> 关闭连接 -> 退出。需要 `RpcServer` 持有 in-flight 表
   （可与 Phase 6 服务端取消共用）。

## 7.5 Phase 11 Performance Engineering

指标：QPS / Latency / P99 / P999 / Memory / CPU。

工具链：

```
perf + flamegraph   CPU 热点
heaptrack           分配与内存增长
ASan/UBSan preset   已就绪（linux-asan / linux-ubsan）
```

重点怀疑对象（基于当前实现的预判）：

- `RpcCodec::Decode` 中 `RetrieveAsString` 产生一次 string 拷贝；
- `PendingWrite::bytes` 在排队与发送间的移动是否真正零拷贝；
- `pending_calls_` 的 unordered_map 节点分配频率；
- `EventLoop` 单线程下 `DoPendingFunctors` 的 mutex 竞争。

## 7.6 Phase 12 Benchmark 对比

对比对象：NebulaRPC / gRPC / bRPC。

场景：

```
echo RPC（小 payload 高并发）
large payload（接近 16MB 上限）
concurrent request（多连接 + 单连接多路复用）
timeout scenario（慢服务端 + 超时率）
```

输出：统一格式性能报告（进 notes）。
